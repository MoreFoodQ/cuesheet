# 規劃：榜單聚合、等級配置與更新追蹤

狀態：第二版（2026-11-18），第一版經 Gemini 4 Hydrogen（high）審查後修訂。第一階段已完成（v0.5.0），第二階段已完成（v0.6.0），第三階段已完成（v0.7.0），第四階段已完成（v0.8.0）。

## 要回答的問題

「我現在用 Opus 5.5 medium，它在各榜幾分？有沒有同等級或更強、但更省的模型？我的訂閱能不能用？」

以及在背景持續追蹤：新模型、CLI 新版本、榜單更新，有變化就通知。

## 原則

- 不同榜單的分數不相加、不平均、不互相換算。每個榜單分開列，各自標明測什麼。
- 成本的定義各不相同（每題、每次成功、整套測驗總額、每 token），只在同一個榜單內比較。
- API 成本不等於訂閱額度。訂閱的真實成本是「做一件事吃掉那家幾 % 額度」，要靠實際使用量測。在量到之前，不拿 API 價格替使用者自動換模型。
- 只用允許程式取用的來源。Artificial Analysis 的網站條款禁止用程式擷取資料，所以只走使用者自己申請的 API 金鑰。
- 榜單資料只存在本機 `data/`，不進 Git，不轉發原始資料。每個來源都標明出處與資料日期（CC BY 的來源也要）。
- 每個來源獨立快取、獨立失敗。一個網站改版，只影響它自己那張表。

## 「我能不能用」分三層

| 層級 | 意思 | 從哪裡知道 |
|---|---|---|
| 平台有 | 這個模型和推理強度在 CLI 的模型清單裡 | `cue models` |
| 已設定 | `runners.json` 有對應的代理，接力能派給它 | `runners.json` |
| 現在有額度 | 那家的額度還沒用完 | `cue` |

輸出時三層分開標示，例如「平台有、未設定」或「已設定、額度用完」。

## 等級設計

- 最小單位是「模型＋推理強度」。同一個模型不同強度可以差很多（Opus 5.5 從 low 到 max 跨了四個等級）。
- 等級以 AA 綜合智能為準，寫在 `tiers.json`，附 AA 指數版本（目前 v5.0.1）。AA 改版時重新校正界線。
- 兩種用途，兩種規則：
  - 設定用（`runners.json` 寫 `"tier"`）：固定區間，例如 L1 ≥ 55、L2 50–55、L3 45–50、L4 35–45、L5 < 35。固定區間才不會出現「A 和 B 同級、B 和 C 同級，A 和 C 卻差 5 分」的矛盾。
  - 查詢用（`cue rank`）：以基準模型的分數往下 3 分以內加上所有更高分的，避免卡在區間邊界、錯過只差一點但便宜很多的模型。
- 沒有分數時：
  - 已淘汰、從清單消失的模型：保留最後一次的分數，標「已淘汰」與資料日期。
  - 缺某個推理強度：不內插估算（各強度的分數不是線性的），只列鄰近強度給人參考，自動選模時不選它。
  - AA 完全沒有的模型：標「未分級」，改列其他榜的分數；不進自動選模，除非使用者在覆寫檔人工指定等級。
- 能力限制：同等級不代表能互相替補。`agy` 和 Claude Code 在無人模式下不能執行需要核准的 shell 指令，Codex 可以。任務要能標 `requires_shell`，自動選模時排除做不到的平台。

## 依任務難度選模型

使用者的需求（2026-11-18）：難的任務要找同等級或更聰明的模型，簡單的任務優先派比較弱、比較省的模型。

- 任務可以標難度，例如 `"difficulty": "hard"`、`"normal"`、`"easy"`，或直接寫最低等級 `"min_tier": "L2"`。
- 難（hard）：只考慮等級不低於基準模型的候選，同分時偏好分數高的。例如以 Opus 5.5 medium（L3）為基準，就找 L3 以上。
- 一般（normal）：同等級裡挑真實成本最低的。
- 簡單（easy）：從低等級往上找，先派最弱但足夠的模型（例如 Flash、Luna、Hydrogen low），省下高階模型的額度。
- 這和「Flash 不當替補」不衝突：Flash 不替補難的工作，但它本來就是簡單工作的首選。
- 同樣的規則也寫進 Claude Code Skill，讓 Claude 互動派工時照用。
- 實作放在第三階段（查詢、建議）與第四階段（接力自動選模）。

## 名稱對照（model_map）

- `model_map.json`（進 Git）：每個「模型本體」一筆，記錄它在各 CLI 的呼叫方式（模型 id、推理強度怎麼傳、看哪個額度）和在各榜的寫法。例如 Opus 5.5 同時在 Claude Code 和 agy 裡，兩邊的 id 和額度都不同。
- 本機覆寫檔（不進 Git）：使用者手動補對照、忽略不相關的模型、指定未分級模型的等級。優先順序：人工覆寫 > `model_map.json` > 自動比對 > 對不上。
- 自動比對只做確定性的正規化：統一大小寫、`.` 與空白、拆出推理強度、去掉「Default Fallback」之類的註記。不用模糊比對自動配對，因為 `gpt-6.1-sol` 和 `gpt-6.2-sol` 只差一個字元。模糊比對只用來在對不上時提出候選。
- 對不上的只提醒重要的：三家 CLI 有、但某個榜對不到的模型。

## 訂閱額度的真實成本

每次接力執行前後，即時查一次該代理的所有額度（5 小時、每週分開記），寫進 `data/relay/usage_samples.jsonl`。每筆樣本附上有效性標記，只有「乾淨」的樣本才算進成本：

| 標記 | 情況 | 處理 |
|---|---|---|
| 乾淨 | 前後都是即時資料、沒跨重置、任務完成 | 計入 |
| 跨重置 | 重置時間變了，或用量變少 | 排除 |
| 舊快照 | 前後任一次不是即時資料 | 排除 |
| 未完成或撞上限 | 任務失敗，或用量到 99% 以上 | 排除（另外統計） |
| 疑似並行 | 執行期間有其他工作在用同一家的 CLI（從各 CLI 的 session 紀錄是否有別的寫入判斷） | 排除 |

- 額度百分比多半是整數，短任務常看到 0% 或 1%。所以不算每筆的平均，而是「總消耗 ÷ 次數」，0、1、0、1、0 會收斂成每次 0.4%。
- 依「任務 × 模型 × 推理強度 × 額度種類」分組。少於 5 筆標「樣本不足」，不參與自動決策。

## 分階段（依審查建議調整順序）

量測額度成本不需要任何榜單，越早開始累積樣本越好，所以提到第一階段。自動選模放到有真實成本資料之後。

### 第一階段：版本檢查與開始量測（已完成，v0.5.0）

1. **CLI 版本檢查**：讀三家 CLI 已安裝版本，比對最新版。Codex 查 npm registry；Claude Code 與 agy 先確認有沒有「只檢查、不安裝、不卡互動」的方式，沒有就只顯示目前版本。結果放進「需要注意」。
2. **額度樣本記錄**：`cue relay` 每次執行前後記錄額度，寫入 `usage_samples.jsonl`。不改變現有接力行為。

完成標準：
- 版本檢查連跑五次，不觸發安裝、不卡住、不花額度；某個 CLI 不存在時只影響它自己那一項。
- 用假代理模擬五種情況（正常、跨重置、舊快照、撞上限、並行），樣本標記都正確；實跑一次接力後多一筆樣本。

### 第二階段：免金鑰榜單、名稱對照與 `cue rank`（已完成，v0.6.0）

實際做法：必要來源為 Arena Agent、Epoch（ECI 與依強度分列的 CursorBench、SciCode、CritPt）、OpenRouter（GPQA Diamond）、models.dev。名稱對照以固定規則為主，`model_map.json` 只記例外。LiveBench 與 Terminal-Bench 兩個選用來源還沒做（都要解析網頁，較脆弱）。新模型（例如 GPT-6.2 Sol）在這些榜上要過幾天才有，所以第三階段的 AA 仍然重要。


1. `cue boards --refresh`：抓 Arena、Epoch、OpenRouter、models.dev（必要），LiveBench、Terminal-Bench（選用，可關閉）。每個來源寫自己的快取檔，附抓取時間、榜單日期、狀態、出處。
2. `model_map.json` 與覆寫檔。
3. `cue rank <模型> --effort <強度>`：每個榜一張表，標出基準模型、同級或更強的候選、成本、時間、三層可用狀態、出處。缺指定強度時改列鄰近強度並標示。預設只列三家 CLI 有的模型，`--all` 列全部。

完成標準：
- 不用任何金鑰就能更新；模擬某個來源壞掉時，其他來源照常更新，壞掉的保留舊資料並標「舊」。
- `git status` 確認榜單資料都沒進 Git。
- 名稱對照測試涵蓋三家，且不會把 `gpt-6.1-sol` 配到 `gpt-6.2-sol`。
- `cue rank claude-opus-5-5 --effort medium` 每張表都有內容或明確的「沒有資料」說明，不會報錯或空白。

### 第三階段：接上 Artificial Analysis 與等級表（已完成，v0.7.0）

實際做法：AA 只走官方免費 API，每次更新 4 次請求。新增 `cue tiers`；`cue rank` 的 AA 表標等級，基準模型的等級寫在開頭。一個榜超過上限時先留比基準便宜的。`cue models` 還沒顯示等級，改在第四階段一起做。

1. 使用者自己申請免費金鑰，放在 `config.json`（不進 Git）或環境變數 `CUESHEET_AA_KEY`。
2. 先用金鑰實際打一次 API，確認欄位、已淘汰模型、每題成本是否都有。
3. 建立 `tiers.json` 與分級邏輯；`cue rank` 和 `cue models` 顯示等級與同級建議。這一階段只建議，不自動改接力設定。

完成標準：
- 程式碼裡沒有任何對 AA 網頁的請求；所有含 AA 資料的輸出都標「資料來源：Artificial Analysis」。
- 沒有金鑰或超過每日次數時，正常降級並提示怎麼設定。
- 已淘汰的模型在更新後仍保留分數並標「已淘汰」；缺強度時不內插；未分級的模型有人工等級時套用人工等級。

### 第四階段：依真實成本自動選模（已完成，v0.8.0）

實際做法：等級寫在任務上，不寫在 `runners.json`。任務加 `difficulty`（hard、normal、easy）或 `min_tier`、`max_tier`，候選是 `runners.json` 裡所有代理。hard 依 AA 分數高到低；normal 在每個候選都有 5 筆以上乾淨樣本時，依「估計還能跑幾次」排序，否則照 `default_order`；easy 由弱到強。沒寫難度的任務行為不變。

1. `cue relay --stats`：列出各任務、各模型的樣本數、平均每次消耗、估計還能跑幾次。
2. `runners.json` 可以寫 `"tier": "L3"`：執行時排除未分級、不符能力限制（`requires_shell`）、額度不足的模型，在剩下的模型裡依真實成本挑。真實成本樣本不足時，退回使用者寫的固定順序。

完成標準：
- 用合成樣本驗證只算乾淨樣本、少於 5 筆標樣本不足。
- `cue relay <任務> --dry-run` 印出 `"tier"` 實際解析成哪個平台、模型、強度，以及挑選理由；現有接力測試全部通過。

### 第五階段：主動通知

- `cue watch`：每天由 Windows 工作排程器執行一次，檢查新模型、CLI 新版本、接力模型可升級、榜單出現同級更省很多的模型。
- 有變化才通知，同一件事只通知一次。Windows 通知失敗時，改寫進提醒檔，下次執行 `cue` 時顯示在「需要注意」。

完成標準：
- 連跑兩次而資料沒變時，第二次不通知。
- 排程執行沒有變化時不跳任何視窗。
